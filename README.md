# BankingSystem

В этом репозитории реализован backend банковской системы на Java 25: доменная модель, бизнес-сервисы и REST API для управления пользователями, банковскими счетами и финансовыми операциями.

Приложение построено на Spring Boot 4, использует Spring Security для аутентификации и разграничения прав доступа, Spring Data JPA и PostgreSQL для хранения данных. Проект разделён на два сервиса: `bank-service` и `rates-service`, взаимодействующих через Apache Kafka. Для проверки бизнес-логики и интеграций используются JUnit 5, Mockito и Testcontainers.

## ТЗ

### 1. Цель приложения

Приложение предназначено для автоматизации основных банковских операций в backend-системе из двух сервисов:

- **bank-service**: пользователи, банковские счета, финансовые операции и конвертация валют;
- **rates-service**: предоставление и обновление валютных курсов.

Система должна поддерживать:

- управление пользователями и их банковскими счетами;
- выполнение пополнений, снятий и переводов;
- расчёт комиссий;
- хранение и просмотр истории операций;
- конвертацию денежных сумм;
- получение актуальных валютных курсов через Kafka.

### 2. Роли и права

В системе предусмотрены две роли:

**CLIENT**: просмотр собственных банковских счетов, выполнение финансовых операций, просмотр истории операций и управление списком друзей.

**ADMIN**: управление пользователями и банковскими счетами, просмотр информации о счетах и операциях системы.

Аутентификация реализована с использованием Spring Security. Доступ к данным и операциям ограничивается в зависимости от роли пользователя и принадлежности банковского счёта.

### 3. Что хранит система

**bank-service:**

- пользователи и их учётные данные;
- роли пользователей;
- связи между пользователями в списках друзей;
- банковские счета и их балансы;
- финансовые операции и начисленные комиссии.

**rates-service:**

- текущие курсы USD и EUR относительно RUB;
- время последнего обновления каждого курса.

Валютные курсы хранятся в памяти `rates-service`. В `bank-service` используется локальный кэш с ограниченным сроком актуальности.

### 4. Основные сценарии

#### 4.1. Управление пользователями

Система позволяет создавать пользователей и получать информацию о них.

Для пользователей предусмотрены:

- получение собственного профиля;
- просмотр пользователей с фильтрацией;
- добавление и удаление пользователей из списка друзей;
- просмотр собственного списка друзей.

Список друзей используется при расчёте комиссии за денежные переводы.

#### 4.2. Банковские счета

Система поддерживает создание банковских счетов, просмотр информации о счёте и получение баланса.

Каждый счёт принадлежит определённому пользователю. Клиент может работать только со своими счетами.

Дополнительно реализовано получение баланса в выбранной валюте.

#### 4.3. Пополнение и снятие средств

Пользователь может пополнить свой банковский счёт или снять с него средства.

При выполнении операции система должна:

- проверить существование счёта;
- проверить права доступа;
- убедиться, что сумма положительная;
- при снятии проверить достаточность средств;
- изменить баланс;
- сохранить запись о финансовой операции.

#### 4.4. Переводы между счетами

Пользователь выбирает исходный счёт, счёт получателя и сумму перевода.

При выполнении перевода:

- проверяется существование обоих счетов;
- проверяется принадлежность исходного счёта;
- рассчитывается комиссия;
- проверяется достаточность средств с учётом комиссии;
- изменяются балансы отправителя и получателя;
- сохраняется история перевода.

Размер комиссии зависит от получателя:

| Получатель | Комиссия |
|---|---|
| Другой счёт того же пользователя | 0% |
| Пользователь из списка друзей | 3% |
| Остальные пользователи | 10% |

Перевод выполняется в рамках транзакции базы данных для обеспечения согласованности изменений.

#### 4.5. История операций

Система сохраняет информацию о пополнениях, снятиях и переводах.

Типы операций:

- `DEPOSIT`: пополнение;
- `WITHDRAW`: снятие;
- `TRANSFER_OUT`: исходящий перевод;
- `TRANSFER_IN`: входящий перевод.

Реализована фильтрация истории по банковскому счёту и типу операции, а также получение сумм операций в выбранной валюте.

#### 4.6. Конвертация валют

Пользователь может запросить баланс или историю операций в RUB, USD либо EUR.

Для конвертации используются курсы, полученные от `rates-service`.

При наличии актуального курса в локальном кэше банковский сервис использует его без дополнительного запроса.

Если курс отсутствует или устарел, выполняется запрос к сервису валютных курсов через Kafka.

### 5. Межсервисное взаимодействие

Для обмена сообщениями между `bank-service` и `rates-service` используется Apache Kafka.

Реализованы два механизма взаимодействия.

**Publish/Subscribe**

`rates-service` каждые 10 секунд генерирует новые значения валютных курсов и публикует их в топик `rates.updates`.

`bank-service` получает обновления и сохраняет их в локальном кэше.

**Request/Reply**

Если актуальный курс отсутствует, банковский сервис отправляет запрос в `rates.requests`.

`rates-service` обрабатывает сообщение и отправляет ответ в `rates.replies`.

Для обмена используются общие контракты сообщений, вынесенные в модуль `messaging-contracts`.

### 6. Правила валидации и ошибки

Бизнес-логика должна проверять корректность финансовых операций и ограничивать доступ к чужим данным.

Основные проверки:

- положительная сумма операции;
- существование пользователя и банковского счёта;
- достаточность средств для снятия и перевода;
- запрет перевода на тот же самый счёт;
- соблюдение прав доступа;
- наличие актуального валютного курса при конвертации.

Для обработки ошибок используются предметные исключения, в том числе:

- `DomainValidationException`;
- `EntityNotFoundException`;
- `InsufficientFundsException`;
- `ExchangeRateNotFoundException`;
- `ExchangeRateUnavailableException`.

Ошибки обрабатываются на уровне REST API.

### 7. REST API

API реализовано на Spring Web и разделено по основным областям.

**Пользователи:**

- создание и получение пользователей;
- получение собственного профиля;
- фильтрация пользователей;
- управление списком друзей.

**Банковские счета:**

- создание и просмотр счетов;
- получение списка счетов;
- просмотр баланса;
- получение баланса в выбранной валюте.

**Финансовые операции:**

- пополнение;
- снятие средств;
- перевод между счетами;
- просмотр и фильтрация истории операций;
- получение истории в выбранной валюте.

Для передачи данных используются DTO. Доступ к API контролируется через Spring Security.

### 8. Архитектура

Архитектура решения: многомодульная, с разделением ответственности между банковским сервисом и сервисом валютных курсов.

Основное приложение `bank-service` разделено на четыре модуля:

| Модуль | Назначение |
|---|---|
| `bank-service/domain` | Доменные модели и бизнес-правила |
| `bank-service/application` | Прикладные сервисы, сценарии использования и интерфейсы |
| `bank-service/infrastructure` | Реализации репозиториев, работа с PostgreSQL и кэширование |
| `bank-service/presentation` | REST API, Spring Security, Kafka и конфигурация приложения |

Дополнительные модули:

| Модуль | Назначение |
|---|---|
| `rates-service` | Генерация и предоставление валютных курсов |
| `messaging-contracts` | Контракты сообщений для обмена через Kafka |

Бизнес-логика отделена от деталей хранения данных и межсервисного взаимодействия с помощью абстракций репозиториев и провайдера валютных курсов.

Синхронное взаимодействие с клиентами реализовано через REST API, асинхронный обмен между сервисами осуществляется через Apache Kafka.
